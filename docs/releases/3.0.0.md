nspawn 3.0.0 serves the Docker Engine API with its changes: containers are made, run,
attached to, exec'd in, copied to and from and removed, images pulled and removed,
volumes and networks made and joined. GitLab Runner's docker executor runs its jobs on
nspawn's machines through it, and the `docker` command works with `DOCKER_HOST` set to
it. The API server is a client of the bus service, as the command line is: everything it
does is a method of `org.nspawn`, under the same polkit actions.

## Breaking changes

- **A machine's Docker API socket takes changes.** A machine that mounts
  `/var/run/docker.sock`, `/run/docker.sock` or `/run/nspawn/api.sock` from the host
  read-write (`-v /var/run/docker.sock:/var/run/docker.sock`, compose's
  `use_api_socket`) may make, start, exec in and remove containers, pull and remove
  images, and make volumes and networks. Bound with `:ro`, the socket reads, follows
  logs and kills, and refuses any other change with 403. A reverse proxy or a dashboard
  that only reads should mount the socket `:ro`.
- **A record pulled or built that never ran is an image, not a container.** The API's
  container list, inspect and prune leave it out; `GET /images/json` lists it, and a
  machine made from it is a container.
- **The bus says what failed.** A method or job that fails carries a name under
  `org.nspawn.Error`: `NotAuthorized`, `NoSuchMachine`, `NoSuchImage`, `NoSuchNetwork`,
  `NoSuchVolume`, `NoSuchPath`, `Exists`, `InUse`, `NotRunning`, `AlreadyRunning`,
  `Paused`, `NotPaused` and `Invalid`, `Failed` for the rest. The messages are the
  ones the command line prints.

## Added

- **The host's socket of the Docker API**, `/run/nspawn/api.sock`, opened by
  `nspawn-api.socket`, which the packages ship turned off. Every user may connect;
  polkit decides what each one may do with the bus service's actions (reads and waits
  `org.nspawn.inspect`, logs and changes `org.nspawn.manage`), never asked to prompt.
  Root may do everything. A drop-in with `Symlinks=/run/docker.sock` serves clients that
  only look there. What one socket's clients hold at once is bounded: connections,
  log and event streams, waits and attaches, exec commands; a user other than root
  holds a share of each, so that no user keeps the others or root out.
- **Containers through the API**, made and run by the bus service:
  - `POST /containers/create`: a create's settings become the machine's options. What
    nspawn has no use for is named in the answer's `Warnings`; what would change what
    the container does is refused with 400. A name the API takes that is no machine
    name (`reaper_1`) stays the container's name in the API, and its machine gets one
    made of it.
  - `start`, `stop`, `restart`, `kill`, `pause`, `unpause`, `wait` (`not-running`,
    `next-exit`, `removed`), `update`, `DELETE /containers/ID` and `POST
    /containers/prune`. `AutoRemove` removes the machine once its run ends.
  - `attach`, with the input too: the program gets the client's input, and its end
    when the client closes its writing half; a run whose input an attach holds writes
    its output to it byte for byte, which `docker run -i`, `docker run -it` and `docker
    start -ai` use. A `wait` on the same socket answers once the attach has handed over
    what the run wrote.
  - `exec`: `POST /containers/ID/exec`, `POST /exec/ID/start`, `resize` and `json`, with
    a terminal or with standard output and error apart, the input, variables, working
    directory and user. A command that cannot run exits 127 when it is not found and 126
    otherwise. On a terminal, the end of the input or the client's hangup sends the
    command SIGHUP.
  - `archive`: `HEAD`, `GET` and `PUT /containers/ID/archive`, so `docker cp` works
    both ways, on running containers and on stopped ones, owners and modes kept.
- **Images through the API**: `POST /images/create` pulls with the engine's progress
  messages and its "Image is up to date" and "Downloaded newer image" ends, asking the
  registry for the tag's digest first; `DELETE /images/REF` and `POST /images/prune`
  remove them. An image's ID is its config's digest. An image built here with a name
  without a registry (`nspawn build -t somos/app:1`, which nspawn files under the
  configured registry) goes by that short name too while Docker Hub's image of it is
  not here.
- **Volumes and networks through the API**: create (labels, anonymous volumes; a
  network's IPv4 subnet, internal networks), inspect, list, remove and prune;
  `POST /networks/ID/connect` and `disconnect` with aliases and fixed addresses, while
  the container runs or not. `bridge`, `host` and `none` are the pre-defined networks.
  A network keeps the name the API gave it (`e2e_dk.net`) next to its own.
- **On the bus**: `WaitMachine`, `RestartMachine`, `PruneMachines`, `StatPath`,
  `GetVolume` and `ResolveImage`, which tells the local image a name means, as the
  command line reads it or as clients of the Docker API do; both ask it. `CopyFrom` takes `name`, `CopyTo` `extract`, `owner` and
  `no_overwrite_dir_non_dir`; `CreateVolume` labels and anonymous volumes;
  `CreateNetwork` labels and the API's name;
  `PullImage` `image_only`; `PruneImages` `names`; `StopMachine` a signal; `RunMachine`
  an input whose output comes back straight. `ListMachines` and `GetMachine` give
  `last_started`, when the last run that ended started.
- **`-P`/`--publish-all`** publishes each port the image exposes that no `-p` publishes
  to a free port of the host, on `run`, `create` and `start`, and on the bus's
  `publish_all`. `--dns-option` and `--expose` are taken with a warning.
- **`nspawn info`** prints the service's version, its machines by state, its images,
  directories, default backend, log driver and registry, and the host it runs on;
  `-f json` prints the answer, `-f TEMPLATE` a template over it, and it exits 1 when
  the service does not answer. On the bus it is `Info`, which the Docker API's
  `GET /info` answers from.
- **`nspawn images inspect NAME|REFERENCE...`** prints the records of images as JSON,
  or through `-f TEMPLATE`; a reference means the image `ResolveImage` finds, a machine
  made from it when no image is left. `nspawn image` is the same group as
  `nspawn images`.
- **`nspawn volume create --label KEY=VALUE`** and **`nspawn volume ls --filter
  label=...`**.
- **`nspawn system prune --volumes`** removes the unused volumes made without a name,
  which only the Docker API makes.

## Changed

- **`--timezone auto`**, the default, gives a writable root that lacks the host's zone
  a copy of the host's `/etc/localtime` (`Timezone=copy`), which a package such as
  tzdata can replace, instead of systemd-nspawn's read-only bind of it.
- **A variable's value may hold line breaks** (`-e`, compose's `environment`, the API's
  `Env`): it goes into the settings file encoded and reaches the program through the
  image's `/bin/sh`, as an argument with a newline does, under a name of letters,
  digits and underscores. GitLab's `CI_COMMIT_MESSAGE` of a commit with a body is such a
  value.
- **A bare `-e VAR` that is not set is left out** (`run`, `create`, `start`, `exec`,
  `--env-file`, the bus's `env`) instead of refused, so `-e DEBUG` passes an optional
  setting on only where it is set. A start whose variables are all left out keeps the
  ones the machine remembers.
- **A build of a tag replaces the image of that reference** under the tag's local name
  while nothing ran from it, an mkosi build too. A machine that has the name, or an
  image of another reference, keeps it, and the build goes beside it with the same
  reference, into the image an earlier build of the tag put there or else under a free
  name (`app-2`), which a note says; `run`, `create`, compose and the Docker API find it
  by the reference. An mkosi build given a `--name` one of them has is refused. `--force`
  replaces whatever has the name.
- **A line that starts with `<N>`** stays as it was written in the logs, rather than
  becoming its priority.
- **`nspawn exec` keeps a `HOME`** that the machine's or the command's variables give;
  the user's home otherwise.
- **`nspawn restart`** restarts through the bus's `RestartMachine`.
- **`WaitMachine` answers** once the unit's hooks after the end are done, when the
  machine reads as stopped or restarting.
- **`cp` to or from a stopped machine** refuses a path at or below one of its volumes,
  or a source that holds one, as they are mounted only while it runs.
- **The SELinux policy** (module 2.2.0) lets systemd make the `/run/docker.sock` link
  of the drop-in, and nspawn make the missing directories of binds.

## Fixed

- **No line of a machine's output is lost to journald's rate limit.** The unit's
  `LogRateLimitIntervalSec=0` never reached journald, which kept its defaults (10000
  lines in 30 seconds); the hooks drop-in now sets an interval of one microsecond with a
  burst of a million.

## Requirements

As for 2.0.0. A user other than root needs a polkit rule to use the host's socket of
the Docker API, such as `nspawn-wheel.rules`, which the packages ship as an example.

## Known gaps

- Image builds, loads, imports, tags, pushes and commits, container renames and
  exports, swarm and plugins are not served by the API: they answer 501 with "not
  supported".
- A volume of a stopped container is mounted only while it runs: copies to or from it
  are refused until the container starts.
- `nspawn run -i` reads a run's output through the journal, which drops empty lines;
  the API's attach with an input carries it byte for byte.
- `nspawn generate` does not keep the name the API gave a network, and compose refuses
  network names with a `.`.
- The mstack backend stays experimental and untested, as for 2.0.0, and does not serve
  the Docker API.
