nspawn 1.4.0 brings three things compose files ask of the service before
`nspawn compose` (2.0.0) can run them: a machine in another machine's network,
a group with `--user`, and pulls that fetch several layers at once.

## Added

- **`--network container:NAME`**, docker's sidecar pattern: an app machine
  takes the network namespace of a running machine, with its address, its
  hosts and resolv.conf files and nothing of its own; a port its program
  serves is published with `-p` on NAME. NAME can be an app or a booted
  machine on any bridge network, and cannot be removed while a machine names
  it. When NAME stops or restarts, the machine keeps the namespace it joined
  and has to be restarted to join the new one, as with docker. `-p`,
  `--network-alias`, `--dns`, `--dns-search`, `--add-host` and `--sysctl` are
  refused on such a machine, and so is a booted image. `ps` and `inspect`
  show `container:NAME`; the record carries it in `network_container`, which
  an older nspawn ignores.
- **`--user USER:GROUP`**, as docker takes it: the group, a name of the
  image's group file or a number, becomes the primary and only group of the
  program. systemd-nspawn's `User=` has no place for it, so the getent
  stand-in nspawn binds answers it; a group name the image lacks is refused
  before the start, with docker's wording.

## Changed

- **`pull` fetches three blobs at a time**, as docker does. The layers of an
  image came one after the other, each waiting for the round trip of the
  last. Every transfer has a bar of its own on a terminal, `pull` says of
  each blob when it is downloaded, a blob a manifest names twice is fetched
  once, and a download cut short by another's failure takes its part file
  with it.

## Fixed

- **`--backend auto` on a freshly booted host** chose flat: overlayfs is
  listed in `/proc/filesystems` only once its module is loaded, which nothing
  had done yet. nspawn loads it before deciding.
- **`top` right after a restart** could still list systemd-nspawn's own child,
  which sits in the machine's cgroup until it has become the machine's init;
  `top` now waits for the init and leaves that child out.
- **A health probe that printed more than 4 KiB** was cut off by its reader,
  which closed the pipe on it: past the pipe's buffer the probe died of
  SIGPIPE and counted as a failure, so a `curl` of a large page made a
  healthy machine unhealthy. The output is drained now and the first 4 KiB
  kept, as docker does.
- **`create` with the short reference of a local image** (`nspawn create
  fedora:44 web` after `nspawn pull fedora:44`) pulled the image again under
  the name it already had and was refused for that. The reference is compared
  as the record spells it, as `run` compares it.
- **The service kept every job and every command it ever ran** while it
  stayed busy (an `events` or a `logs -f` client keeps it so), a small object
  each. It keeps the last hundred that ended and lets the older ones go; the
  `Jobs` and `Processes` properties list what is kept.

## Security

A review of the whole source found three ways an image could reach the host
through nspawn, all closed here; none was a boundary a caller could cross
without the manage action, but an image is not a caller.

- **A control character in an image's config** (a newline in `WorkingDir`,
  `User`, `Env`, `Entrypoint` or `Cmd`) went into the machine's settings file
  as it was, where the rest of the value became directives of the image's
  choosing, `Bind=/:/host` among them. Such an image is refused at pull, build
  and create, `--entrypoint`, the command and `--tmpfs` options are checked
  the same way, and the settings file is never written with one.
- **A symlink of the image leading out** (`etc -> /etc` on the host) was
  followed on the host by what looks into the image ahead of a start: the
  seeding of a named volume, the getent stand-in's checks, the group lookup
  of `--user`, and the mount points a read-only machine gets made. Every path
  is now resolved inside the image, as systemd-nspawn resolves it, so nothing
  of the host is read or made through an image's link.
- **A read-only machine's mount points** were made through the same links;
  see above.

## Requirements

As for 1.3.0. The test matrix is Ubuntu 24.04 (systemd 255), Fedora 44 (259,
SELinux enforcing) and Arch (262).
