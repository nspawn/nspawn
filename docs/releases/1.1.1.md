nspawn 1.1.1 shows how far a pull or a push got, closes a few ways local users
and machines could reach more than they should, and fixes what 1.1.0 broke.
Upgrading is recommended for every host.

## New

- **Progress of downloads and uploads.** `pull` and `push` draw a bar for each
  blob, with its size, speed and time left, when standard error is a
  terminal; in a pipe or a log the lines are the same as before. The bars were
  drawn by the service since 1.0.0, where nobody saw them. On the bus, jobs
  send `JobProgress(o job, s item, t done, t total)` a few times a second
  while a blob moves; see `docs/DBUS.md`.

## Security

- **The state directory is root's alone.** `/var/lib/nspawn` was readable by
  every local user. Its layers hold whatever the images hold, setuid programs
  and device nodes among them, which worked on the host for anyone who
  reached them; its records hold the machines' environment, and the writable
  layers of overlay machines what they wrote. Everything below it is now
  root's alone (0700), but for the generated files an mstack machine binds
  from inside its user namespace; the directory itself can only be passed
  through (0711). An existing one is closed when the service starts, the
  packages ship it so, and `/var/lib/machines` is made 0700 when nspawn
  creates it, as systemd does.
- **Settings files are root's alone.** `/etc/systemd/nspawn/NAME.nspawn`
  carries the variables given with `-e`, passwords and tokens often; it is now
  written 0600, and one an earlier version left open is closed at the next
  start.
- **Names cannot leave their directory.** `images rm`, `rm`, `stop`,
  `inspect`, `exec`, `shell` and `logs` joined the name they were given to
  paths below the state directory without checking it, so a name like
  `../../x` reached files elsewhere; it is refused now.
- **exec keeps the machine's root away from its command until it runs.**
  Between entering the machine and running the program, the command's process
  could be traced from inside a machine with private users, and held the
  service's descriptors. It is now not dumpable until it execs, descriptors
  other than its streams are closed, and the machine's leader is held by a
  pidfd so that a PID given to another process meanwhile is never entered.
  The command also gets the machine's capability bounding set, as docker exec
  gives the container's, where it had the host's whole one; nspawn-selinux
  lets the service narrow it.
- **Job signals go to their owner.** What a job says (`JobOutput`,
  `JobProgress`, `JobRemoved`) and how a command ends (`Exited` and the
  properties of its object) were broadcast to every client of the bus; they
  now go to the client that started it, as their objects already answered
  their owner and root alone.

## Fixed

- App machines on the bridge did not start on a host booted with
  `ipv6.disable=1` (1.1.0).
- `pull --force`, `create --force` and `build --force` took a machine off the
  boot list that an administrator had put there with `machinectl enable`
  (1.1.0). A replacement now leaves that alone; only a restart policy of
  nspawn's own is undone with it. Removing a machine takes it off the boot
  list once it is gone, and a unit systemd cannot disable no longer leaves
  a removal half done.
- `stop --force` whose kill systemd refused reported the machine stopped even
  when it was not (1.1.0); the unit's stop job now follows such a kill, so
  the machine goes.
- The service could stop answering while it stopped a machine with a restart
  policy on a busy host: the systemd signals it waited for piled up unread
  and held up every reply on its connection (1.1.0).
- `ps` without `-a` listed machines that were only starting or closing
  (1.1.0); it lists what runs and what is being restarted, like docker ps. A
  unit that is still up after its machine ended reads as `closing`.
- `stop` of a machine without a record of nspawn's, whose unit keeps
  restarting it (a `Restart=` of an administrator's), said it was not running;
  it stops the unit now. A `stop` while a `start` of nspawn's prepares the
  same machine is refused instead of releasing its network under it.
- A virtual machine of machined counts as running again when `images rm` or a
  `--force` replacement asks whether a name is in use (1.1.0).
- `volume prune` without `-f` removed volumes when its standard input was not
  a terminal (1.1.0). As with docker, it now asks on standard input whatever
  it is, and removes nothing without a yes.
- A pull that downloads for longer than an hour lost its blobs to an
  `images rm` running meanwhile.
- A write probe left in `/var/lib/machines` by a crash could make a later
  pull fail (1.1.0).
- `cp` out of a machine could hang on a file the machine turned into a fifo
  during the copy.
- `inspect` and `ps --json` gave a wrong `machine_path` for a machine whose
  name starts with a digit.
- `logs` works while machined cannot answer; the hint of `images rm` names
  `nspawn rm --force`; errors about a unit's state name the unit.

## Requirements

As for 1.1.0: systemd 255 or newer with systemd-nspawn and machined,
overlayfs, `ip` and `nft`; `cp` needs Linux 5.6 or newer, `exec` Linux 5.3.

## Known gaps

The gaps of 1.1.0 remain: limits and policies apply at the next start, `cp`
has no `-L`, `-a` or tar streams, there is no per-machine delegation, no
signature verification of pulled images and no IPv6 on the bridge. Images
pulled with 1.0.0 show their image labels once they are pulled again.
