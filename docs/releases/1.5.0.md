nspawn 1.5.0 verifies the signatures of the images it pulls. Every image on
hub.nspawn.org is signed twice by the workflow that builds it, and a pull now
has one of those signatures verify before a single layer comes down. Other
registries get a policy of their own in the configuration file.

## Added

- **Signature verification at pull.** The hub's build workflow
  (nspawn/mkosi-definitions) signs every image with cosign, once with the
  project's key and once keyless with the workflow's identity through
  Sigstore, and keeps the signatures on the registry as OCI referrers of the
  image. `pull`, `run` and `create` fetch those bundles after resolving the
  manifest and before downloading anything, and verify them offline against
  the project's key and the workflow's identity, both built into nspawn, with
  the transparency log entry and the timestamp each bundle carries, against
  the Sigstore trusted root the binary embeds. One of the two has to verify:
  `pull` then says who signed the image and remembers it (`signed_by` and
  `signed_at` in `inspect`, `GetImage`, `ListImages` and the pull job's
  result; a machine made with `create` inherits them). An image without a
  valid signature is refused with the reason; `--no-verify` on the three
  commands skips the check for that command, as docker's
  `--disable-content-trust` does (`PullImage` takes it as the `verify`
  option). Images of other registries are pulled as before.
- **A signature policy per registry** in `/etc/nspawn/nspawn.toml`: a
  `[registries."host"]` table names the cosign public keys (`key`, `keys`)
  or the keyless `identity` and `issuer` the images may be signed with, and
  says whether a signature is `required` (default), whether its transparency
  log entry must verify (`rekor`, default) and the `trusted_root` of another
  Sigstore deployment. A table for `hub.nspawn.org` replaces the built-in
  policy, and `verify = false` turns the check off for a registry, the hub
  included. The service reads the keys when a pull needs them and checks them
  when it starts.

## Fixed

- **The overlay module under SELinux.** Choosing the default backend runs
  modprobe when overlayfs is not listed yet, which on a Fedora host that
  booted a moment ago it never is; the service's domain could not execute
  kmod, so the pull went flat without a word. modprobe runs in kmod's own
  domain now, and the suite unloads the module before the check.

## Requirements

As for 1.4.0. Verification needs nothing beyond the registry: the bundles
carry their log entries and timestamps, and the Sigstore trusted root ships
inside the binary (sigstore-verify, the Sigstore project's Rust client, is a
new dependency). The test matrix is Ubuntu 24.04 (systemd 255), Fedora 44
(259, SELinux enforcing) and Arch (262).
